# Test health: 2026-10-21

Upkeep pass: profile, classify per area, refute every merge/delete, apply,
measure. Commits `577b057` (before) to `d418825` (after).

**Conditions.** macOS arm64, 16 cores, rustc 1.99.1, nextest 0.9.149,
jj 0.46.0, warm `target/`. The `git` on PATH was a wrapper costing ~47 ms
per call; "fast git" below is a plain binary at ~5–15 ms. Host load varied
from 5 to 60 during the runs: treat single-test times as ±2x.

## Findings

- **The suite's time is git process spawns.** About 37% built fixtures
  (`add` + `commit` per commit, 85 processes for the 42-commit mouse
  fixture) and 62% were the app's own reads (~15 per `App::new`). Test time
  followed spawn count: ~260 ms of test time per git call with the slow
  wrapper vs ~51 ms with plain git, under 16-way contention.
- **Startup read the branch twice.** `branch_start` then `load` →
  `branch_refresh` repeated 5–7 reads. Fixed in the product (`cd21f0e`):
  git calls per start 14→9 clean, 18→11 on a feature branch, 7→6 detached;
  jj snapshots 2→1. git `refresh` is a no-op, so all of it was branch reads.
- **`[vcs] git` / `DEBRIEF_GIT`** (`844e0b7`) lets users and the suite run a
  faster git. Fixtures honour it through `tests/common` `git_program()`.
- **Fixtures via `git fast-import`** (`092bc32`): one import plus
  `read-tree -u --reset` per repo, 3 processes. Setup spawns 6,975→2,399.
  Plain `git init` (`--template=` drops `.git/info`, and four tests write
  `info/exclude`); dates rise to now−1 s, above the 1.6e9 floor
  `vcs_git.rs` asserts.
- **3 s quiet-window settles** were idle time: each step causes a known 0,
  1 or 2 events, all within 620 ms. Now `settle_events(app, rx, n)` with a
  20 s bound per event (`8d0b19a`). Where a later assert is negative
  (`a_follow_load_in_flight...`, `branch.rs`), an exact count matters: a
  short quiet tail can pass before the in-flight load lands.
- **Watcher negative checks** reused the 5 s positive timeout; `quiet()` is
  5x the 300 ms debounce. The 600 ms drain stays: a trailing second event
  was seen at 921 ms. No rescan timer or second debounce exists (notify on
  FSEvents uses latency 0, `NoDefer`).
- **Keymap/help/clue unit tests** built real repos (281/155/112 git calls
  for the top three; 69/38/28 s with slow git). They now use
  `test_support::fake_app`; fake and real were compared over 226,512
  keymap lookups, all equal. The fake's root must be a real dir
  (`Review::open` canonicalises it) and its `show` must return 1 file
  (`tree_has_files` feeds focus).
- **jj 0.46 colocates by default**, so `JjEnv::new(false)` had been building
  colocated repos and the non-colocated path was untested. Now
  `--no-colocate`; history-only jj fixtures are built with git then
  `jj git init --git-repo` (`2a24496`). `vcs_jj` 6.7 s → 3.5 s.

## Rejected or refuted

- **A template repo copied per test.** `cp -R` of the fixture cost
  0.5–2 s on this host (endpoint scanning), slower than `fast-import`.
  nextest's process-per-test model would also need a cross-process cache.
- **One shared `App` across help contexts.** Contexts mutate mode, focus,
  visual and commit-list state; sharing leaks it. One fake App per context.
- **Deleting the default-snapshot tmux run** in
  `tui_e2e::jj_snapshot_and_no_snapshot`. A mutant hardcoding
  `snapshot: false` at `main.rs` `vcs::open` fails only this run; the flag
  parse test (`src/cli.rs`) and `working.rs` never go through `main.rs`.
- Merged, not refuted: `jj_log_renders_moves_and_quits` into the
  `--no-snapshot` run (it checked nothing the remaining runs miss).

## Remaining bottleneck

The app's own git reads under a slow git wrapper: with fast git, `vcs_jj`
(110 s of test time) and `working` (84 s) lead; `tree_watcher_fires...`
(13 s) is bounded by its positive fires and drains. A further product win
was measured but not done: `current_branch` + `branch_revset` take 5 calls
per refresh; one `for-each-ref` plus `symbolic-ref` would take 2 (risk:
unborn, detached and no-trunk cases).
