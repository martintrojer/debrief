# debrief: catch up with what the agents did, and answer back

Status: approved design (brainstorm 2026-10-09, Q1–Q20). No code yet.
Related: ramble (`~/hacking/ramble`), redline.nvim (`~/hacking/redline.nvim`,
prior art for the export format), tuicr (what this replaces in the loop),
mu and murmur (where the agents run).

## Problem

Many pi agents run under mu, each in its own workspace; murmur shows their
state. Catching up with them uses four tools:

```
agent produces something → you notice it's new → you read it        → you comment on lines → comments go back to the agent
   (md docs, commits)       (murmur, lazygit)      (ramble, lazygit)    (tuicr)               (paste into pi)
```

lazygit is used only for its commit list and commit drill-down. tuicr is
used only to comment, and ramble calls it even for prose, which is a jump
out of the reader for every comment. tuicr is ~107k lines for forges,
PRs, profiles and updates; this loop needs a few percent of it.

The thing that unifies the loop is not a viewer. It is **review**: a
comment on some lines of some file at some revision, collected into a
batch, handed back to whoever made it.

## Approach

Share the comment model and the hand-back; keep the viewers separate.

| Piece | Role |
|---|---|
| `debrief-review` crate | Comment model, one open batch per repo in the user cache dir, markdown export, hand-back command. No UI, no VCS. |
| ramble | Stays the prose reader. Gains a comment mode on source lines. Never becomes a diff viewer. |
| `debrief` binary | The commit catch-up tool: log with new/seen state, continuous commit diff, comments on diff lines. Never renders markdown; hands `.md` files to ramble. |
| hand-back | One configured command, used by both. Default clipboard; a small script routes to the owning mu agent. |

No shared UI crate yet (Q6). debrief copies the patterns it needs from
ramble (keymap, key clue, `g?` help, motions, visual mode, sidebar,
launchers). Extract a shared crate only once both tools show what they
really share.

## 1. `debrief-review` crate

Caller's view:

```rust
// ramble, visual selection + `c`:
let mut r = Review::open(&cache_dir, repo_root)?;
r.add(Comment::on_file("docs/plan.md", 12..=18, excerpt, body))?;

// debrief, on a diff line:
r.add(Comment::on_diff("src/x.rs", rev, Side::New, 40..=44, excerpt, body))?;

// either, `<leader>rr`:
let md = r.to_markdown();
handback::send(&cfg.send, &md, repo_root)?;
r.clear()?;
```

**Types.**

- `Comment { id, path, rev: Option<Rev>, side: Option<Side>, lines: RangeInclusive<u32>, excerpt, body, created }`.
  `path` is repo-relative; `lines` are 1-based source lines (new or old
  side for diffs). `excerpt` is the source text of those lines at capture
  time, truncated to 40 lines.
- `Rev { commit: String, change: Option<String> }`: git commit, or jj
  commit plus change ID. `None` means the working copy (ramble on a file).
- `Side { Old, New }`, only for diff comments.

**Repo root.** The VCS root (`.jj` or `.git`, the nearest one; a jj
workspace is its own root). A file outside any VCS uses its directory.
The root is canonicalised so ramble and debrief agree.

**Storage.** One JSON file per root:
`<user cache dir>/debrief/reviews/<blake3(root)[..16]>.json`, holding the
root path and the comments. Every mutation is read-modify-write under an
`flock` on a sibling `.lock`, then written by rename, so ramble and debrief
open on the same repo can't lose each other's comments. `Review::open`
never creates a file until the first `add`. Nothing is written into the
repo.

**API.** `open`, `comments()`, `add`, `edit(id, body)`, `remove(id)`,
`clear`, `to_markdown`, `reload` (other process changed it; callers poll
the file's mtime, as ramble's watcher does).

**Markdown export.** Derived from redline.nvim's format, reworded for an
agent receiving feedback rather than reviewing:

````markdown
# Review feedback

The reviewer left these comments on your work in <root>.
Address each item, and reference its number in your reply.

## Item 1
- File: docs/plan.md
- Lines: 12-18
- Revision: (working copy)
```
<excerpt>
```
<body>

## Item 2
- File: src/x.rs (new side)
- Lines: 40-44
- Revision: kmxqpwrz 3f2a9c1e "feat: parse things"
```diff
<excerpt>
```
<body>
````

Items are ordered by file, then line. The preamble is configurable
(`[send] preamble`), like redline's `prompt_lines`.

**Hand-back.** `[send] command = [...]` gets the markdown on stdin and
`DEBRIEF_ROOT=<root>` in its environment. If no command is configured,
or it exits non-zero, it falls back to the clipboard over OSC 52 and says
so in the status line. The batch is cleared only after a successful send
(the clipboard counts).

**`debrief-send` script** (shipped in the repo, not in the crate): looks up
`DEBRIEF_ROOT` in `mu workspace list --all --json`; if an agent owns it,
`mu agent send <agent> "$(cat)"`; otherwise exit 1, so the caller falls
back to the clipboard.

## 2. Comment mode in ramble

- **Capture.** Visual `c` comments on the selection's source lines; normal
  `cc` on the cursor line. The srcmap already maps cells to source bytes
  (yank uses it), so the selection becomes a line range directly. Lines
  and excerpt come from the document on screen, frozen when `c` is
  pressed: the text you see is the text you comment on.
- **Entry.** A one-line prompt at the bottom like `:` and `/`; Enter saves,
  Esc cancels, `C-e` moves the typed text into `$EDITOR` on a temp file
  (the launcher's suspend/resume) and saves on exit if non-empty.
- **Display.** The existing gutter `●`, file-tree markers and `]r` / `[r`
  are driven by the batch for the page's repo root, showing only
  comments with no `rev` (diff comments' lines belong to a revision, not
  the file on disk). `<leader>rl` lists every comment. On a commented line
  the status line shows the first comment's first line; `K` shows the full
  comment(s), falling back to the link preview when there's no comment.
- **List.** `<leader>rl` opens a picker of the batch (file:line, body).
  Enter jumps (opening the file if needed), `C-d` removes, `C-e` edits
  (the picker takes typed text, so plain letters filter).
- **Send.** `<leader>rr` exports and hands back; the status line says
  how it went ("Review sent (N comments)" / "Review copied to clipboard
  (N comments)"). The hand-back API doesn't report the recipient.
- **stdin pages** can't be commented (no path); `c` says so.
- **Removed.** tuicr polling in `src/review.rs` and
  `src/app/review_glue.rs`, the `[review] command` setting, and the three
  default tuicr launchers (`<leader>rr`, `<leader>rw`, `<leader>rd`).
  `[[launch]]` still lets anyone bind tuicr.
- **Config.** `[review] enabled = true`; `[send] command`, `[send] preamble`
  shared in meaning with debrief's.
- Raw view (`gR`) supports the same keys; its lines are source lines.

## 3. The `debrief` binary

- **Start.** `debrief [path]`, default the working directory. jj when a
  `.jj` is found above the path, otherwise git; otherwise an error.
- **`Vcs` trait** (CLI-backed):
  `root()`, `log(revset, limit) -> Vec<CommitInfo{commit, change, author, time, summary, parents}>`,
  `show(commit) -> {message, files: Vec<FileDiff>}` from unified diff
  output (`git show --format= -p`, `jj diff -r <c> --git`). Diffs are
  parsed into files, hunks and lines with old/new line numbers.
- **Seen state.** `<cache>/debrief/seen/<blake3(root)>.json`: seen commit
  IDs and, for jj, seen change IDs. A commit is **new** if neither is
  seen, **updated** (jj only) if its change is seen but this commit isn't
  (the agent rewrote it), otherwise **seen**. Opening a commit marks it
  seen; `m` marks every listed commit seen. The first time debrief opens
  a repo it marks every listed commit seen, so you start from "nothing
  new" rather than 200 new commits.
- **Log view.** Newest first: marker (new / updated / blank), short
  change or commit ID, age, author, summary. The cursor starts on the
  oldest new or updated commit, else the top. `r` (and a file watch on
  `.git/HEAD`, `.git/refs` or `.jj/repo/op_heads`) reloads.
- **Commit view.** Message, then every file's unified diff in one scrolling
  stream, coloured (no syntax highlighting in v1). File-list sidebar like
  ramble's (`C-w h/l`, Enter jumps). `]f` / `[f` move between files,
  `]c` / `[c` between hunks; `]]` / `[[` open the next / previous commit
  (`K` stays "show the comment here", as in ramble).
  ramble's motions, visual mode, yank, `/` search and key clue.
- **Comments.** Visual `c` / normal `cc` on diff lines. The range is the
  selected lines' new-side numbers, or old-side if the selection has only
  removed lines; a selection mixing sides uses the new side and puts both
  in the excerpt as diff text. `rev` is the commit and change ID. Same
  gutter markers, `]r` / `[r`, `<leader>rl`, `<leader>rr`.
- **ramble hand-off.** Enter on a changed `.md` file's header runs a
  launcher (default `ramble ${file}`) on the working-copy path, if it
  exists.
- **Editor.** `<leader>o` opens `$EDITOR` at the working-copy file and
  line under the cursor, from any row of the commit view: a removed line
  goes to the new-side line where it was, a hunk header to its first
  new line, a file header to line 1. From the log it opens the commit's
  first changed file at its first hunk. The TUI suspends and comes back
  on the same row. The commit's line number can drift if the file has
  changed since; deleted or missing files are refused. Other launchers
  as in ramble.
- **Help.** `g?` lists the live keymap, tested against it as in ramble.

### Working copy (Q21–Q24, added 2026-10-09)

- **git** (read-only except that git itself refreshes split-index
  timestamps on any read): when the tree is dirty (tracked changes against `HEAD`, or
  untracked files that aren't ignored), the log gets a "Working copy" row
  on top (`✎ N files`). Enter opens it in the commit view; untracked
  files show as added. Nothing is written: no index refresh.
- **jj:** debrief snapshots the working copy (`jj util snapshot`) before
  loading the log, opening `@`, reloading and returning from the editor,
  so `@` shows your uncommitted edits. `--no-snapshot` skips it and shows
  `@` as of the last jj command.
- **Comments:** on new or context lines they are anchored like ramble's
  (no revision, line numbers of the file on disk), so ramble shows them
  too; on removed lines, to `HEAD` (git) or `@-` (jj), old side.
- **Refresh:** git watches the tree (ignoring `.git` and ignored paths)
  and refreshes the row; jj refreshes on `r`, on opening `@`, after the
  editor, and when the agents' own jj commands move the operation log.

| # | Decision | Why |
|---|---|---|
| Q21 | jj may snapshot; `--no-snapshot` opts out. | jj sees uncommitted edits only after a snapshot; the agents snapshot constantly anyway. It leaves files alone but rewrites `@` like any jj command. |
| Q22 | git: a synthetic Working copy row; jj: `@` is the row. | Same commit view for both, no new screen. |
| Q23 | New-side comments carry no revision; removed-line comments anchor to the base commit. | ramble and debrief then agree on the same file. |
| Q24 | git watches the tree; jj refreshes on actions and op-log moves. | Watching in jj would mean a snapshot on every save. |

## Out of scope (v1)

Forges and PRs; staging or any write to a repo; side-by-side diffs; syntax
highlighting; word-level diff; re-anchoring comments after rewrites;
comment threads or replies; the cross-workspace inbox (next, Q19); a
shared TUI crate with ramble; hg/Sapling.

## Testing

- `debrief-review`: unit tests for ordering, export (snapshot), add/edit/
  remove/clear; a two-process test that interleaves adds under the lock;
  hand-back fallback when the command fails.
- ramble: e2e tests in the existing harness for `c` / `cc` ranges in
  rendered and raw views (lists, tables, code blocks, front matter rows),
  the prompt and `C-e`, gutter and `]r`, `<leader>rl`, send with a fake
  command. Rendering snapshots unchanged.
- debrief: `Vcs` tests against throwaway git and jj repos created in the
  test (skipped when `jj` is absent); diff parser tests (renames, binary,
  no newline at EOF, empty commits); seen/updated logic across a jj
  rewrite; comment ranges on mixed selections; e2e key tests like ramble's.
